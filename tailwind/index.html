02

fundamentos técnicos

A diferença é quando o CSS é produzido

Styled Components — runtime

JS Button.tsx 
const Button = styled.button`
  padding: ${p => p.large ? "16px" : "8px"};
  background: #e60000;
`;
  1. Template literal (JS) parseado no navegador
  2. Hashing do nome de classe a cada estilo
  3. Injeção de <style> no <head> durante o render
  4. Browser recalcula estilos do documento

Tailwind CSS — build-time

TW Button.tsx 
<button className="px-4 py-2 bg-red-600
  rounded-lg hover:bg-red-700">
  Confirmar
</button>
  1. Engine Oxide (Rust) escaneia as classes no build
  2. Gera um .css estático, purgado (8–15 KB gzip)
  3. Navegador recebe <link> cacheável, parse nativo
  4. Runtime: zero JavaScript de estilização

A serialização de props (${props => ...}) reexecuta a cada render, e é o padrão da documentação e o dominante nos times.

03

o fundamento menos citado

O modelo do React desaconselha CSS em runtime

01

Concurrent rendering (React 18+)

Injetar regras CSS entre yields do React força recálculo de estilos contra a árvore inteira: padrão de layout thrashing documentado por Sebastian Markbåge (core team) e reproduzido em benchmark por Nolan Lawson.

02

React Server Components

styled-components depende de Context API e efeitos no render, exclusivamente client-side. Usar no App Router exige 'use client' em tudo, abrindo mão do modelo server-first.

03

Recomendação oficial

Estilos estáticos via <link rel="stylesheet">; valores dinâmicos via inline style. É exatamente o modelo do Tailwind, e o oposto do modelo do styled-components.

07

performance

Peso entregue ao navegador (app SaaS típico)

Tailwind (purgado)

8–15 KB

CSS gzip · zero runtime JS

CSS Modules

12–25 KB

CSS gzip · zero runtime JS

styled-components

35–55 KB

20–40 KB de CSS + ~15 KB de runtime JS competindo pelo main thread

Por que importa: desde mar/2024 o INP substituiu o FID nos Core Web Vitals. Serialização de estilo em runtime compete pelo main thread exatamente nas interações, sobretudo em Android de entrada. Contraponto justo (Sanity, 2025): entre as libs runtime, o styled-components ainda é a mais rápida — o problema é o modelo, não a implementação.

08

avaliação honesta

Tailwind: o que entrega e o que custa

Entrega

  • Performance por arquitetura: zero JS de estilo, CSS purgado, RSC/streaming sem adaptação
  • Consistência por restrição: tokens em escala fechada; desvio vira exceção visível no review
  • Iteração rápida: sem nomear classes, sem CSS órfão; dead code impossível por construção
  • Ecossistema: shadcn/ui, Radix, Headless UI; IA gera Tailwind por padrão

Custa

  • Curva real: 2–4 semanas até fluência do time
  • "Class soup" sem disciplina: exige cva/tailwind-variants + prettier-plugin
  • Estilo dinâmico de dado vira inline style / CSS variable, mudança de hábito
  • Risco corporativo não nulo: layoffs em jan/2026 (mitigado: output é CSS puro)
09

sem invenção

Onde o styled-components ainda vence

01

Estilização dinâmica por props

${props => ...} é mais expressivo; o equivalente Tailwind (cva + mapas de variantes) funciona, mas com mais cerimônia.

02

Theming em runtime (multi-tenant / white-label)

Caso natural do ThemeProvider, e a v6.4 trouxe createTheme via CSS variables, compatível com RSC.

03

CSS completo co-locado

Seletores complexos e animações elaboradas em sintaxe CSS real, no mesmo arquivo, sem escape hatches.

Quando NÃO migrar: SPA client-side saudável, sem problema medido de INP. Migração por moda é desperdício.
10

recomendação

Estratégia: incremental, medida, sem big bang

Projetos novos

Tailwind v4 + cva/tailwind-variants + prettier-plugin-tailwindcss + tokens via @theme + shadcn/ui ou Radix.

Se o time rejeitar utility-first: CSS Modules, vanilla-extract ou Panda CSS: o inegociável é build-time, não a sintaxe.

Anti-recomendação

Reescrita big bang de base grande: o custo excede o benefício em praticamente todos os cenários documentados. A v6.4 comprou tempo: use-o para migrar com calma, não para não migrar.

Migração de base existente

  1. Instalar Tailwind ao lado do styled-components: coexistem sem conflito
  2. Todo componente novo nasce em Tailwind
  3. Migrar componentes tocados por features (regra do escoteiro)
  4. Usar codemods e o upgrade tooling oficial
  5. Medir INP/LCP antes e depois: justificar com dados do próprio produto

A sintaxe é detalhe.

A decisão arquitetural é build-time.
